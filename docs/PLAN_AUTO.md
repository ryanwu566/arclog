# ArcLog 自動模式：實作計畫

> 2026-11-14 動工前寫的計畫，之後照著做；每個階段結束時測試要全部通過才提交（分支 `feat/auto-mode`）。
> 實際做到哪裡、哪些驗證過、哪些沒有，寫在第 6 節的勾選框（做完才勾，附驗證方式）和 PR 說明，不會回頭把計畫改成「都完成了」。
> 原本的計畫在 `docs/PLAN.md`，這份只寫這次的改動。

## 1. 為什麼要改

實測回饋：

1. 球員不會花時間校正和標記，拍完就要看到結果。
2. 球員不會乖乖架在正側面：有人直接從投籃者背後拍。
3. 同一個球館裡有其他人在投別的籃框，畫面裡會有別人的球。

目標流程：打開網站 →「開始練投」→ 照畫面引導架好手機 → 投籃 →「停止」→ 很快看到報告。
全程不點籃框、不標記球。上傳現有影片也一樣自動。原本的半自動工具保留，移到「修正」和「進階」。

不變的原則：影片只在本機處理；實拍影片、畫面、人像不進 repo（提交前跑 `tools/check_staged.py`）；
沒有實拍驗證的數字不寫成準確度；寧可說「這個角度量不準」，也不給看起來很精確的錯數字。

## 2. 動工前查證的結果

### 2.1 公開資料集（細節寫進 `docs/DATA.md` 第 4 節）

- **Basketball Shooting Robot**（The University of Arizona，Roboflow Universe，`the-university-of-arizona-th1yv/basketball-shooting-robot`）：
  搜尋結果與 Roboflow 官方部落格（2026-08）說約 9.8k 張、有 ball 和 rim，另外還有人和投籃動作的標籤。
  第三方的 GitHub 發布頁寫「CC BY 4.0、9,612 張、ball + rim」。
  **Roboflow 的資料集頁面擋掉自動讀取（HTTP 403），所以授權和類別名稱這次沒有直接核對到。**
  依目前看到的資訊，它**沒有籃板類別**。
- 籃板：搜尋到幾個名稱或類別裡有 backboard 的公開資料集，同樣因為 403 沒辦法核對授權和內容，列為候選。
- 決定：
  1. 授權和類別不憑網頁記憶，改由程式在下載後核對：`prepare_public.py` 讀匯出檔裡的 `README.roboflow.txt` 的授權那一行
     和 `data.yaml` 的 `names`，授權不是 CC BY 4.0／CC0／Public Domain 或找不到需要的類別就停下來。
  2. 類別依名稱對應（別名表：`ball/basketball`、`rim/hoop/basket`、`backboard/board`），不靠編號。
  3. 籃板只出現在部分資料集時，混在一起訓練會讓模型學到「沒標的籃板是背景」。對策是**補標**：先用有籃板標註的資料訓練，
     再用那個模型替 Arizona 的影像補上高信心的籃板框（`training/pseudo_label.py`），補過的標註和人工標註分開記錄。
  4. 輸出的模型固定三個類別：0 ball、1 rim、2 backboard。網站依 `manifest.json` 的 `classes` 欄位對應類別。

### 2.2 iPhone Safari 的相機與背景分析（細節寫進 `docs/SHOOTING_GUIDE.md` 和 `docs/NEXT_STEPS.md`）

查到的（社群與 WebKit bug tracker；Apple 沒有正式文件寫記憶體上限）：

- `getUserMedia` 需要 HTTPS；Safari 分頁會記住網站的相機權限，拒絕之後要重新整理頁面才能再問。加到主畫面的網頁每次啟動都會再問。
- **頁面被切到背景、鎖定螢幕時，iOS 會把相機軌道設成 muted**（WebKit bug 172200 的行為），回到前景才恢復。錄影會中斷，背景分析也會停。
- `MediaRecorder`：Safari 14.1 起支援，輸出 MP4（H.264）；iOS 18.4 beta 曾有 MP4 錄影失敗的 bug（已修）。
- WebGPU：Safari 26（iOS 26）起預設開啟；更舊的 iPhone 只能用 WASM。
- iOS 的分頁記憶體限制比桌機嚴，數字沒有公開。

決定：

1. **邊錄邊分析，但不依賴即時分析一定跟得上**：相機畫面每隔幾幀送一張給偵測（依裝置實際速度自動調整），同時用 `MediaRecorder`
   把完整影片每秒一段存進 IndexedDB（不是放在記憶體）。按停止時：即時分析的密度夠（每秒至少 10 張）就直接出報告；
   不夠就對錄好的影片補分析，畫面顯示預計還要多久（用剛才量到的每秒處理張數估計）。
2. 錄影時用 Screen Wake Lock 讓螢幕不要自動關；相機軌道 muted、頁面切到背景時記下中斷的時間並提醒，
   回到前景後繼續錄，報告註明中斷的時段。
3. **影片不能丟**：分析失敗、頁面當掉、重新整理之後，首頁會找到 IndexedDB 裡還沒處理完的錄影，可以重新分析或下載。
4. 實際在 iPhone 上要等多久**沒有實機量過**，介面顯示的是當下量到的速度，PR 和文件寫明未驗證。

## 3. 設計

### 3.1 偵測：三個類別，沒有籃框類別的模型也能用

- `core/yolo.js` 新增 `decodeMulti`：一次解出多個類別（每個類別各自 NMS），結果帶 `cls`。舊的 `decodeDetections` 不變。
  Python 的 `arclog/yolo.py` 同步，用共用測試向量比對。
- `manifest.json` 每個模型多一個 `classes`（例如 `{"ball": 0, "rim": 1, "backboard": 2}`）；現有的 COCO 模型只有 `{"ball": 32}`。
- 模型沒有籃框類別、或籃框偵測不穩定時：**退回讓使用者點兩下**（籃框前緣、後緣），其他步驟照樣自動。

### 3.2 自動校正（`core/autocal.js`）

- 收集多幀的籃框框，取「最常出現的那一個籃框」（畫面裡可能有好幾個籃框，用位置分群，選框最大、出現最穩定的那群，
  使用者也可以在預覽時點選要哪一個）。
- 穩定值：框的四個邊各取中位數，同時算離散程度；離散太大（手機在動、偵測不穩）就判定「還不穩定」。
- 前緣、後緣：框的左右兩端。高度取框裡籃框鐵圈的高度：只標鐵圈的框取中線；連球網一起標的框取上緣往下一小段
  （依模型的 `rimBox` 設定，下載資料後看預覽圖決定）。
- 比例：框寬對應的是鐵圈**外緣**（約 48.5 公分：內徑 45 公分加兩邊鐵條），換算成內徑。
  入框角度在籃框座標系裡算，u 和 v 用同一個比例，**比例差多少都不影響角度**，只影響過框位置（進球判定）和球的大小過濾。

### 3.3 自動判斷鏡頭角度（`core/viewangle.js`）

偏角 θ：鏡頭光軸和「投籃方向的垂直線」的夾角。0 度＝正側面；90 度＝正後方或正前方。

兩個獨立的線索，都用比例，不用知道距離：

1. **籃板的寬高比**：籃板 1.8 × 1.05 公尺，正側面看是一條細線，越轉向正面越寬：寬 ≈ 1.8·sin θ ＋ 厚度·cos θ。
   高度會因為鏡頭仰角變短，用籃框橢圓的扁平程度（≈ sin 仰角）修正。
2. **籃框中心和籃板中心的水平距離**：籃框中心在籃板正面前 0.375 公尺，畫面上看起來是 0.375·cos θ，用籃框寬（直徑）當尺。

兩個合起來 `θ = atan2(籃板寬／1.8, 偏移／0.375)` 的形式，再加上球飛行中變大或變小（離鏡頭變近或變遠）判斷正負號
（往投籃者後方偏、或往籃框後方偏）。沒有籃板偵測時只能用球的大小變化，結果標成「不確定」。

分級（門檻**先用 `tools/camera_study.mjs` 模擬驗證再定**，根據寫進 `docs/EVAL.md`）：

| 等級 | 偏角（初始提案） | 報告 |
|---|---|---|
| A | 30 度內 | 完整報告；自動套用偏角修正 tan(真) = tan(量)·cos θ |
| B | 30 到 60 度 | 完整報告，標「誤差較大」，說明原因（偏角估計的誤差被放大） |
| C | 超過 60 度 | 只有出手數和命中率；入框角度不顯示，或在「實驗功能」裡標成「粗估 ± X 度」 |

驗證方式：模擬裡量「偏角估計的誤差」和「修正後入框角度的誤差」對 θ 的變化，取誤差開始超過 1 度、超過 3 度的位置當門檻。

**實驗功能（評估後才決定做不做）**：用球的視覺大小（深度）加上已知重力和時間戳重建 3D 軌跡。
在模擬裡加上偵測框大小的雜訊、漏偵測，看誤差範圍；只在誤差範圍誠實標示的前提下開放，預設關閉。

### 3.4 自動分球與進球判定（`core/autoshots.js`）

建立在現有的 `findShots`（Python 也有一份，共用向量）之上，**不改它**，在後面加一層：

1. **只留往我們這個籃框投的球**：軌跡要有實際的偵測點靠近籃框（不是只靠延長線），而且靠近籃框時球的大小要和
   「籃框旁邊的球應有的大小」（球徑／籃框徑 ≈ 0.53）相符。別的籃框的球離鏡頭遠很多，大小對不上；
   運球、傳球本來就過不了 `findShots` 的拋物線條件。
2. **進球判定改用過框之後的運動**：
   - 球通過籃框平面之後，依擬合的軌跡預測「如果沒有被球網擋住」的自由落體位置。
   - 進網的球會被球網拖慢、水平方向被拉到籃框中間，而且常常被球網遮住幾幀才在網子下方出現。
   - 從籃框旁邊或後面經過的球（側拍看起來也「穿過」籃框）是**自由落體**，水平速度不變，會沿著預測的軌跡繼續走。
   - 彈框的球在過框後又往上或往外。
   - 判定：明顯偏短／偏長 → 沒進；過框後彈起 → 沒進；過框後的點符合自由落體（含水平速度不變）→ 沒進（麵包球、從旁邊經過）；
     過框後明顯比自由落體慢、或被遮住後在網子下方出現 → 進球。都不明確時退回原本的幾何判斷，標成「不確定」，報告裡提醒確認。
3. **偏角超過 60 度**（C 級）時軌跡在畫面上幾乎是上下走，拋物線條件過不了，改用另一套簡單的分球：球升到籃框以上再落回籃框附近算一次出手，
   進球依「落到籃框下方、在籃框寬度內、速度被拖慢」判斷。

### 3.5 合成測試場景（`core/synth3d.js`、`demo/scene3d.js`）

現在的示範畫面是正側面的 2D 圖，量不出鏡頭角度。新增一個 3D 的合成場景：

- 3D 拋體（含空氣阻力），籃框（鐵圈當圓環碰撞）、籃板、球網（拖慢並往中間拉），可以產生空心、擦框進、擦框出、
  麵包球（短、長、左右偏）、從籃框後面經過的球。
- 針孔相機（和 `tools/camera_study.mjs` 同一套投影），可以放在任何偏角、距離、高度。
- 背景有另一個籃框和別人在投的球。
- 每一幀角落有幀號條碼。**模擬偵測器**（只在示範和測試用）讀條碼找到這一幀的真實答案，加上位置雜訊、漏偵測、誤偵測，
  輸出和模型一樣格式的 ball、rim、backboard 框。這樣網站的整條自動流程（含相機錄影）都可以在已知答案下驗證。
  真的 ONNX 模型路徑另外測（現有 COCO 模型偵測球、籃框退回點兩下）。
- 瀏覽器測試用 Chrome 的假相機（`--use-file-for-fake-video-capture`）播放合成場景的影片，跑「開始練投 → 停止 → 報告」。

### 3.6 網站

- 首頁：主按鈕「開始練投」；次要「上傳影片」「示範」。
- 錄影畫面：相機預覽＋引導框（籃框放這裡、籃框和投籃者都要入鏡、橫拿手機），即時顯示籃框偵測狀態和鏡頭角度等級；
  偵測到籃框穩定後才可以開始（沒有籃框類別的模型：點兩下籃框）。邊錄邊分析，按停止出報告。
- 上傳影片：自動校正 → 判斷角度 → 偵測 → 直接出報告（籃框偵測不到時才請使用者點兩下）。
- 報告：最上面先講結論（命中率、平均角度、穩定度、前後半差異），角度等級的說明，再給細節；每一球可以點開看軌跡疊圖，
  自動結果錯了才進「修正」（改進球與否、刪除、重新標點）。原本的半自動標記移到「修正」和「進階」。
- iPhone 介面問題：標題不換行、檔名縮短（iPhone 的亂碼檔名顯示成「影片」加時間）、safe area 和 Safari 工具列（`100dvh`、
  `env(safe-area-inset-*)`）、手動校正的示意圖和不合理點位的提醒（點在籃框高度以下很遠、前後緣幾乎在同一點、垂直線歪超過 10 度）。

## 5. 風險

| 風險 | 影響 | 對策 |
|---|---|---|
| Roboflow 頁面讀不到，授權和類別沒有直接核對 | 用到授權不對或類別不同的資料 | 下載後由程式核對 `README.roboflow.txt` 和 `data.yaml`，不符就停；`docs/DATA.md` 寫明未核對 |
| Arizona 資料集沒有籃板 | 三類別模型的籃板偵測不好 | 補標；籃板偵測不到時，鏡頭角度只用球的大小變化估，標成「不確定」，不套用修正 |
| 在使用者訓練好之前，網站的模型（COCO）沒有籃框類別 | 自動校正用不了 | 退回點兩下籃框，其他照樣自動；介面寫明原因 |
| 籃框框的定義（只框鐵圈或連球網）隨資料集不同 | 籃框高度差幾公分，過框位置偏 | `manifest.json` 的 `rimBox` 設定；看預覽圖決定；入框角度不受比例影響 |
| 偏角估計在實拍時的誤差未知（籃板框不準、被投籃者擋住、鏡頭變形） | 分級錯、修正錯 | 門檻保守；修正量太大（B 級）時標「誤差較大」；寫明是模擬得來 |
| 模擬偵測器只在合成畫面上有效 | 測試通過不代表實拍可用 | 文件與 PR 明說；真模型路徑另外測 |
| 側拍時球從籃框旁邊或後面經過，看起來像進球 | 命中率算錯 | 用過框後的運動判斷；不確定的標出來讓使用者確認 |
| iPhone 錄影時鎖螢幕、切 App、記憶體不足 | 錄影中斷、分析停 | Wake Lock、muted 事件、IndexedDB 分段存；中斷時段寫進報告 |
| iPhone 上的處理速度未知 | 等很久 | 依當下速度調整取樣、顯示預估時間；沒有實機數字，PR 寫明 |
| Chrome 的假相機不等於 iPhone 的相機 | e2e 通過不代表 iPhone 可用 | 列為需要使用者實機測試的項目（`docs/NEXT_STEPS.md` 的清單） |
