# 模型卡：ArcLog 籃球偵測模型

這個資料夾放網站和 `tools/analyze.py` 共用的偵測模型（ONNX 格式）。階段 A、B、C 的模型只做一件事：**在一張畫面裡找出籃球**；
自動模式用的階段 B3 模型另外找**籃框**和**籃板**（網站用它們自動校正、判斷鏡頭角度）。
進球與否、入框角度都是後面的軌跡邏輯算的，不是模型的輸出。

`manifest.json` 裡每個模型的 `classes` 告訴網站「哪一類是什麼」（例如 `{"ball": 0, "rim": 1, "backboard": 2}`）；
沒有 `rim` 的模型，網站會請使用者點兩下籃框。三類別模型另外有 `rimBox`：訓練資料的籃框框是只框鐵圈（`rim`）還是連球網（`rim+net`）。

`manifest.json` 是模型清單，網站的模型選單和 Python 工具都讀它。`tools/sync_models.py` 會把這個資料夾複製到 `web/models/`
（網站部署的根目錄是 `web/`，讀不到上一層）。

> **目前只有階段 A 的模型，而且它在實拍影片上的表現還沒有量過。** 評估結果見 `docs/EVAL.md`。

### 為什麼信心門檻設得這麼低

這個模型不是為了「遠遠的、有點模糊的飛行籃球」訓練的，遇到這種球通常只給很低的信心分數。
在合成畫面上的測試中，門檻設成一般常用的 0.25 時幾乎找不到球；降到 0.05 才找得齊。
門檻低會多出不少誤報，這些交給後面的軌跡邏輯處理：只有連起來符合拋物線、最高點高於籃框、下降時靠近籃框的偵測才會被當成一次投籃。

### 評估結果

- **實拍影片：待實測。** 目前沒有任何實拍影片。
- 合成畫面上的結果見 `docs/EVAL.md` 第 2 節。合成畫面比實拍乾淨很多，那些數字**不代表實拍準確度**。

### 已知或預期會失效的情況

以下情況還沒有用實拍影片驗證過，是依模型的性質和合成測試推斷的：

- **球在畫面上太小**：模型的輸入只有 640×384，影片會先縮小（1080p 影片縮成三分之一）。
  合成測試裡球縮小後的直徑大約 18 像素，找得到；比這更小的情況沒有測過，預期會越來越難找到。
  離得越遠球越小，這是拍攝指南建議 8 到 10 公尺、不要更遠的原因之一。
- **動態模糊**：每秒 30 幀、光線不足時球會拉成一條橢圓，分數會更低。
- **球和背景顏色接近**、**背光**：球變成剪影或融入背景。
- **畫面裡有其他圓形的東西**：其他的球、頭、燈、牆上的圓形標誌都可能被框出來。固定不動的會被濾掉，會動的可能造成多抓或串錯軌跡。
- **同時有兩顆以上的球在飛**，或旁邊有人運球、傳球。
- **不是側拍**：從正面或斜後方拍，軌跡不是拋物線的形狀，後面的邏輯會全部濾掉。
- **慢動作影片**：軌跡邏輯假設影片是正常速度（用時間判斷哪些偵測屬於同一球）。
- **球被擋住**：飛行途中經過人或柱子後面，偵測點太少時會漏掉整球。
- **進球判定**：側拍看不到球是往左還是往右偏，涮框、擦板等情況只能猜。網站上的進球判定永遠只是建議，可以一鍵改正。

自動偵測找不到球、或模型載入失敗時，網站會說明原因並讓使用者改用半自動標記；半自動流程完全不依賴模型。

## 階段 B 和階段 C 訓練完之後

`training/export_onnx.py` 會自動把新模型登記到 `manifest.json`。之後請在這份文件補上：

1. 「模型一覽」的狀態改成已提供，並仿照階段 A 加一節，寫明：檔案大小和 SHA-256、從哪個權重開始訓練、訓練了幾輪、
   用了哪些資料（階段 B 要列出資料集的名稱、版本、網址和授權，見 `docs/DATA.md` 的標示出處；階段 C 寫影片支數和球數，不寫檔名和人名）。
2. `docs/EVAL.md` 的比較表（`python training/evaluate.py --dataset <資料集> --write-doc` 會自動更新）。
3. 這個模型特有的失效情況（例如只在某一個場地拍的影片上訓練，換場地可能變差）。

要把新模型設成網站的預設：把 `manifest.json` 最上面的 `"default"` 改成新模型的代號，再執行 `python tools/sync_models.py`。
請先確認它在測試影片上真的比較好再改。
